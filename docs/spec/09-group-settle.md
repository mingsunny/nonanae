# 09. 그룹 정산 (최소 송금)

그룹 내 모든 지출을 바탕으로 "누가 누구에게 얼마를 보내야 하는지"를 최소 건수의 송금으로 계산해 보여주고, 내가 보낼 상대방 계좌번호를 빠르게 복사하는 화면.

- **상태**: 초안

## 3. UI 구성

### 3.1 헤더

- 08 §3.1과 동일(08/09/10 공용)

### 3.2 하단 탭바 (그룹 내부 GNB)

- 08 §3.2와 동일(08/09/10 공용) — 현재 탭은 "정산"

### 3.3 안내 문구

- "가장 적은 횟수로 정산할 수 있도록 계산했어요. 내가 보낼 계좌는 탭하면 복사돼요. 지출을 등록하면 정산 결과도 실시간으로 바로 반영돼요."
- 지출을 추가/수정/삭제할 때마다 실시간 재계산
- 별도의 "정산 확정" 이벤트나 알림 없음

### 3.4 송금 목록

- 정렬: 내가 보낼 송금을 금액 내림차순으로 맨 위에 배치 → 그 외(다른 사람 간 송금)는 이름순으로 뒤에 나열
- 송금 행: 보내는 사람 → 받는 사람, 금액
- 내가 보낼 항목에만 추가로 노출: 받는 사람 은행·계좌, "탭해서 계좌번호 복사" 힌트(자세한 동작은 §4 참고)
- 다른 사람 간 송금은 계좌 정보를 아예 렌더링하지 않음(복사할 필요가 없으므로)

### 3.5 빈 상태

| 조건 | 문구 |
|---|---|
| 지출 자체가 0건 | "아직 등록된 지출이 없어요." |
| 지출은 있지만 전원 잔액이 0 (예: 번갈아 결제해서 각자 낸 돈과 부담할 돈이 정확히 같아진 경우) | "정산할 금액이 없어요. 모두 정확히 나눠 냈어요." |

## 5. 데이터

- 지출 1건 안에서 참여자별 분담액이 어떻게 정해지는지(균등 나머지 배분, 비율/금액 반올림 처리)는 11에서 등록 시점에 이미 계산·확정됨 — 09는 그 결과값을 사람별로 합산만 함(11 §데이터 참고)
- 멤버별 balance(잔액), paid(결제 합): 08의 모든 지출을 훑어서 사람별로 "결제한 금액 합"과 "부담한 분담액 합"을 각각 더한 뒤, `balance = 결제 합 − 부담 합`으로 계산
- 최소 송금 트랜잭션: `[{from, to, amount}]` — 받을 사람들과 보낼 사람들을 각각 금액 큰 순서로 정렬한 뒤, 가장 크게 보낼 사람과 가장 크게 받을 사람부터 매칭해서 거래를 만들고, 다 갚지 못한/다 받지 못한 만큼은 다음 순번과 이어서 매칭하는 방식으로 반복
  - 예: A +12만(받을 돈), B +3만(받을 돈), C -10만(보낼 돈), D -5만(보낼 돈) → ① C(10만)-A(12만) 매칭 → C→A 10만 송금, A는 2만 남음 ② D(5만)-A(2만) 매칭 → D→A 2만 송금, D는 3만 남음 ③ D(3만)-B(3만) 매칭 → D→B 3만 송금. 결과: C→A 10만 / D→A 2만 / D→B 3만, 총 3건
  - 이 방식은 "진짜 최소 거래 수"를 보장하진 않음(사람이 많아지면 이보다 더 적은 조합이 이론적으로 있을 수 있으나 다 찾으려면 계산량이 너무 커짐, PLAN 문서의 NP-hard 언급 참고) — 다만 여행 그룹 규모(2~15명)에서는 실무적으로 충분히 적은 건수가 나옴
- 절대값 0.5 미만인 잔액/거래는 부동소수점 오차로 간주해 정산 대상에서 제외(여러 지출의 분담액을 더하는 과정에서 생길 수 있는 계산 오차 방어용)

## 6. 예외 처리

| 상황 | 처리 |
|---|---|
| 지출이 아직 1건도 없음 | 송금 계산 자체를 하지 않고 빈 상태 노출(§3.5) |
| 지출은 있지만 전원 잔액이 0 | 송금 대상이 없어 빈 상태 노출(§3.5) |
| 받는 사람이 앱 미가입 "대기 중" 멤버(12에서 이름만으로 추가됨)라 계좌 정보가 없음 — 결제자로 지정된 지출이 있으면 정산에서 받을 사람이 될 수 있어 실제로 발생 가능 | "계좌 미등록 — {이름}님에게 직접 확인해주세요" 방어 문구, 복사 UI 비활성화 |
